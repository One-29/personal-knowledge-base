# 设计文档体系（docs/）

本目录是「个人知识库管理」项目的**设计文档唯一来源**（single source of truth）。
顺序是：先有这里的设计，后有 GitHub Issue，再后才有代码。

```text
docs/
├── README.md              # 本文件：文档地图 + 写作规范（先读这里）
├── workflow.md            # 开发流程规范：步骤/DoD/内容归属表/简洁原则
├── design/                # 设计文档（按思考顺序编号，向下依赖）
│   ├── 01-requirements.md # 产品需求 PRD：定位/范围/NFR/用户故事/流程/决策（v0.4 已拍板）
│   ├── 02-modules.md      # 模块拆分：判据 / 边界 / 依赖方向 / 时序 / PR 规划（v0.3 草案）
│   ├── 03-data-model.md   # 数据模型：ER / DDL 草案 / 状态机 / 存储选型（v0.2 已拍板）
│   ├── 04-retrieval.md    # 检索链路：切分 / embedding / 混合检索 / 防幻 / 拒答（v0.2 已拍板）
│   ├── 05-agent-workflow.md   # Agent 多步工作流：规划 / 执行 / 缺料 / 汇总（v0.2 已拍板）
│   ├── 06-evaluation.md   # 评估方案：评估集 / recall@k / τ 校准（v0.1 含首次结论）
│   ├── 07-frontend-design.md  # 前端界面设计：token 系统 / 关键决策（v0.1）
│   └── 08-graph-view.md   # 关联图：边的计算 / 权重合成 / 决策（v0.1）
├── templates/
│   └── module-design.md   # 模块设计模板（= GitHub 子 Issue 模板）
└── issue-map.md           # 本地文档 → GitHub Issue 的映射（建仓后维护，待写）
```

## 写作规范（所有文档必须遵守）

### 1. 头部信息

每份文档第一行是 H1 标题；紧接着是元信息表：

| 字段 | 说明 |
|---|---|
| 状态 | `草案`（未评审）→ `已确认`（已与用户拍板）→ `已实现`（代码已合入） |
| 版本 | 语义化 `v0.1`，每次实质修改递增 |
| 日期 | 最后修改日 `YYYY-MM-DD` |
| 上游 | 依赖的上级文档（如 `01-requirements.md`） |
| 关联 | 对应 GitHub Issue 编号（建仓后填） |

### 2. 文档间关系

- **向下依赖**：`01-requirements → 02-modules → 03/04/05 → 06`，编号即阅读顺序。
- **单一事实**：一个事实只在一份文档里写全；别处引用只写 `见 04-retrieval.md §切分策略`，不复制内容。
- **先变需求，再变设计**：需求变了，先改 `01`，再顺着依赖往下改，保证编号顺序永远成立。

### 3. 设计决策的记录格式

考察重点之一是「独立思考」。每个关键决策用统一小节记录，防止「当时为什么这么选」失忆：

```markdown
### 决策：<一句话结论>

- **决策**：选 A。
- **备选**：B（优缺点一句话）、C（优缺点一句话）。
- **理由**：2~3 句，结合本项目约束（如：无服务器、个人单用户、招新展示性）。
- **代价**：选了 A 放弃了什么，以后什么条件下要翻案。
```

### 4. 伪代码规范（Issue / 接口呈现用）

- 语言标注：数据原型用 `python` 块（后续可直接转 Pydantic 模型），接口签名用 `text` 块。
- 接口描述三件套：`方法 路径` → `请求体` → `响应体`，响应体给状态码分支。
- 只写**契约**（输入输出与副作用），不写实现细节——实现细节属于代码评审阶段。

### 5. 图表

- 流程 / 架构图一律用 **Mermaid**（GitHub 原生渲染，无需图片文件）。
- 每个图配一行「图注」，说明读者该从图里得到什么结论。

### 6. 语言与长度

- 中文写作；专有名词保留英文（FastAPI、PostgreSQL、Issue、PR）。
- 目标读者是「三个月后的自己 + 实验室评委」：能讲穿是第一标准，不堆砌形容词。
- 单份文档超过 300 行说明拆错了粒度，回头拆章节。
