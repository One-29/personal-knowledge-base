## 1. 要回答的三个问题

| # | 问题 | 指标 |
|---|---|---|
| Q1 | 该命中的内容，检索到了吗？ | `recall@k`、`MRR` |
| Q2 | 不该答的问题，拒答了吗？库内的问题，被误拒了吗？ | 拒答准确率、误拒率 |
| Q3 | 切分参数与 τ 取多少合适？ | 参数扫描表 |

## 2. 评估集设计

### 2.1 语料与隔离

- 评估语料放 `eval/notes/*.md`（**固定语料**，保证结果可复现、可对比）。
- 评估在**独立知识库**（`评估语料库`）中运行——与开发库、测试库隔离。

### 2.2 问题与标注（`eval/eval_set.json`）

```json
{
  "question": "TCP 为什么需要三次握手？",
  "expected_doc": "tcp.md",                  // 期望命中的来源文档
  "expected_keywords": ["确认双方", "接收能力"],  // 期望命中的内容特征
  "in_kb": true                              // false = 库外问题（应拒答）
}
```

### 2.3 命中判定（块级，宽松但可测）

一条检索结果算「命中」需同时满足：**来源文档匹配** 且 **块内容含任一期望关键词**。
判定为纯规则，不引入模型打分（可复现）。

## 3. 指标体系

| 指标 | 定义 | 目标 |
|---|---|---|
| `recall@k` | 命中数 / 有关问题数 | ≥ 0.9（k=8，即交给生成层的候选数） |
| `MRR` | 首个命中块排名倒数的均值 | 越高越好（反映"真相关的排前面"） |
| 库外拒答率 | 库外问题被拒答的比例 | 100%（不编造是产品红线） |
| 库内误拒率 | 库内问题被误拒的比例 | ≤ 10%（拒答太激进会伤体验） |
| `no_citation` 率 | 模型有明确内容却零引用的比例 | 越低越好（反映模型遵循引用约束的程度） |

## 4. 方法

### 4.1 检索评估（不消耗 LLM）

对每个库内问题：向量化 → `retrieval.retrieve(top_k=8)` → 判定命中 → 汇总 recall/MRR。
**只消耗 embedding 调用**，可反复跑。

### 4.2 拒答评估（消耗 LLM）

对每个问题跑完整 `ask.answer_question`：
- 库外问题：`refused == True` 记正确（并记录 refusal_reason）
- 库内问题：`refused == False` 且引用非空记正确

### 4.3 参数扫描

| 扫描项 | 候选值 | 观察 |
|---|---|---|
| τ（拒答阈值） | 0.20 / 0.25 / 0.30 / 0.35 / 0.40 / 0.45 | 库外拒答率 vs 库内误拒率 |
| 切分块大小 | 400 / 600 / 800 / 1200 | recall@8 与 MRR |
| 重叠 | 0 / 80 / 160 | recall@8 |
| 召回量 | 向量 10/20/30，关键词 5/10/20 | recall@8 收益是否饱和 |

扫描用 `app/evaluation.py` 的程序化接口，避免手工操作。

## 5. 工具与入口

```text
app/evaluation.py        # 评估逻辑（可复用于 CI / 论文式对比）
eval/eval_set.json       # 评估集（问题 + 标注）
eval/notes/*.md          # 评估语料
python -m eval.run_eval  # 入口：建语料库 → 跑检索与拒答评估 → 输出报告
```

## 6. 评估结论（2026-09-10 首次评估）

**语料**：3 篇笔记（tcp/os/python，共 9 块）+ 12 条样本（10 库内 + 2 库外）。
**说明**：语料规模小、问题与原文措辞接近 —— 结果代表"链路正确性"，不代表大规模知识库的真实难度。

| 项目 | 结果 | 结论/动作 |
|---|---|---|
| recall@8 | **1.000**（10/10） | 检索链路正确；混合检索 + RRF 在清晰语料上首位命中（MRR=1.000） |
| MRR | **1.000** | 期望块全部排在首位，无需 rerank（04 DR3 保持现状） |
| 库外拒答率 | **1.000**（2/2） | 不编造的红线成立 |
| 库内误拒率 | **0.000** | 拒答不过度激进 |
| τ 可分性 | 库内 0.544~0.797 vs 库外 0.353/0.395 | **完全可分**，可用阈值区间 (0.395, 0.544] |
| τ 扫描 | τ≤0.35：库外漏拒；τ≥0.40：库外 100% 拦下且库内 0 误拒 | **默认 τ 由 0.35 上调为 0.45**（区间中段，留安全边际） |

### 6.1 一个重要观察：两道闸的分工

τ=0.35 时库外问题**仍被拒答**，但原因是 **L2 兜底**（模型看到不相关素材后自述"资料不足"，映射为 `low_relevance`），
而不是 L1 拦下。把 τ 提到 0.45 后，同样的问题在 **L1 就被拦下**——省一次 LLM 调用、响应更快、也更稳定
（不依赖模型是否"诚实自述"）。

**这印证了 04 §6 的两级设计意图**：L1 是便宜的前置护栏，L2 是生成后的兜底；两者都要有，
但**能用 L1 拦下的不应留给 L2**。

### 6.2 本次评估暴露的经验

1. **τ 必须用数据校准**：0.35 是拍脑袋的初版值，实测证明它在"库外漏拒"边缘。
2. **τ 扫描不需要跑完整问答**：τ 只影响 L1（纯规则），用检索相似度本地模拟即可
   （`evaluation.simulate_thresholds`）——最初的实现跑了 72 次完整问答直接超时。
3. **评估语料要固定**：`eval/notes/` 与评估库独立于开发数据，保证结果可复现。

### 6.3 后续可做（不在本期）

- 扩大评估语料（50+ 篇、含同义改写问题）后重跑，验证 τ=0.45 是否仍成立；
- 切分参数网格（400/600/800/1200）对比 recall@8；
- 引入 rerank 前后对比（前提：先出现 recall 高但排序差的现象）。
