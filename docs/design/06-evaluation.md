# 06-评估方案（v0.4）

| 字段 | 内容 |
|---|---|
| 状态 | 已实现 |
| 版本 | v0.4 |
| 日期 | 2026-09-20 |
| 上游 | `04-retrieval.md`（切分 DR1 / embedding DR2 / 混合检索 DR3-DR4 / 拒答 DR6） |
| 变更 | v2 多知识库分层基线；五库原子替换；按库与难度统计；重新校准 τ |

本文定义可复现的质量基线。切分算法、检索后端或存储层迁移前后都运行同一份清单，
用相同口径比较结果，避免“功能还能打开”掩盖召回质量回退。

## 1. 要回答的三个问题

| # | 问题 | 指标 |
|---|---|---|
| Q1 | 该命中的内容是否进入候选，并排在什么位置？ | `recall@k`、MRR |
| Q2 | 库外问题是否拒答，库内问题是否误拒？ | 库外拒答率、库内误拒率、拒答原因 |
| Q3 | L1 拒答阈值 τ 取多少合适？ | 阈值扫描、库内/库外最高相似度分布 |

所有指标同时给出 overall、逐知识库与逐难度结果。整体平均值不能掩盖某一个库或困难
样本的回退。

## 2. v2 固定评估集

### 2.1 规模与分层

| 知识库 | 固定文档 | 库内问题 | 库外问题 |
|---|---:|---:|---:|
| 高等数学 | 8 | 10 | 2 |
| 计算机网络 | 3 | 10 | 2 |
| 操作系统 | 3 | 10 | 2 |
| Python | 3 | 10 | 2 |
| 数据库 | 3 | 10 | 2 |
| **合计** | **20** | **50** | **10** |

60 条问题按难度分为：smoke 5 条、basic 15 条、regular 20 条、hard 20 条。每篇固定
文档至少被一条库内问题覆盖；每个库都同时包含库内和库外问题。

### 2.2 清单结构

`eval/eval_set.json` 是版本化清单，语料位于 `eval/notes/<library>/*.md`。

```json
{
  "version": 2,
  "libraries": [
    {
      "key": "networks",
      "name": "评估·计算机网络",
      "notes_dir": "notes/networks"
    }
  ],
  "items": [
    {
      "library": "networks",
      "difficulty": "basic",
      "question": "TCP 为什么需要第三次 ACK？",
      "expected_doc": "01-tcp.md",
      "expected_keywords": ["客户端的接收能力", "第三次 ACK"],
      "in_kb": true
    }
  ]
}
```

加载清单时强制验证：

- 语料目录必须是清单目录内的相对路径，不能通过 `..` 或符号链接越界；
- 库 key、库名、语料目录和同库问题不能重复；
- 库内问题必须指向本库真实文档，所有标注关键词必须真实出现在来源文档；
- 库外问题不能伪造来源文档或关键词；
- 每篇文档必须有库内问题覆盖，每个库必须同时有库内与库外样本；
- 正式基线至少包含 5 个库、40 条问题，并覆盖四档难度。

这些检查把“清单写错”与“检索没命中”分开。标注失真会在调用模型和修改数据库前直接
失败。

## 3. 数据隔离与原子替换

评估固定使用 PostgreSQL 数据库 `knowbase_eval` 和
`data/eval-storage`。入口先检查配置，再通过
`current_database()` 核对 Session 的真实连接；日常库 `knowbase` 和测试库
`knowbase_test` 都不能通过检查。

每次运行按以下顺序更新基线：

1. 为五个库分别创建带“导入中”后缀的候选库；
2. 导入全部固定文档，并逐篇确认状态为 `ready` 且至少有一个块；
3. 只有五个候选库全部就绪后，才在一个事务里删除上一版元数据并把候选库改为正式名称；
4. 事务提交后再清理旧原文目录。

任一文档或任一库失败时，事务回滚并清理所有候选库；上一版五个正式库和原文继续可用。
旧原文清理失败只留下可诊断的孤儿目录，不会反向删除已提交的新基线。

## 4. 指标口径

### 4.1 检索命中

一条候选必须同时满足以下条件才算命中：

1. 候选所属文档名与 `expected_doc` 一致；
2. 候选块至少含一个 `expected_keywords`。

`recall@k = 命中问题数 / 全部库内问题数`。MRR 使用首个合格候选排名的倒数，未命中
明确计 0，不能从分母移除。

### 4.2 拒答

- 库外问题返回 `refused=true` 记为正确拒答；
- 库内问题返回 `refused=true` 记为误拒；
- Q3 只用已取得的最高向量相似度本地模拟 L1，不调用回答 LLM；
- Q2 的模型请求、网络或数据库故障会终止整次评估，不能跳过失败样本后发布虚高指标。

### 4.3 调用量控制

Q1 与 Q3 共用同一批问题向量。60 条唯一问题按 embedding provider 的批大小一次准备，
避免逐题调用，并避免 Q3 再重复向量化。检索模式仍需真实 embedding，但不调用回答
LLM；完整模式会额外对 60 条问题运行完整问答。

## 5. 运行入口

```text
app/evaluation/dataset.py                 # 清单、路径和语料标注校验
app/evaluation/metrics.py                 # overall / 逐库 / 逐难度指标
app/evaluation/runner.py                  # 批量向量、检索、拒答与阈值扫描
eval/environment.py                       # 数据库与原文目录隔离
eval/baseline.py                          # 候选库导入、原子切换与失败清理
eval/reporting.py                         # 稳定 JSON 序列化
eval/run_eval.py                          # CLI 编排
eval/eval_set.json                        # v2 问题与标注
eval/notes/<library>/*.md                 # 固定语料
scripts/run-eval.ps1                      # Windows/WSL Docker 入口
eval/baselines/postgresql-bge-m3-v2.json # 已归档的真实检索基线
```

推荐命令：

```powershell
# Q1 + Q3，并保存可审查的 JSON 基线；不调用回答 LLM
.\scripts\run-eval.ps1 -Retrieval -TopK 8 -ReportPath eval\baselines\postgresql-bge-m3-v2.json

# Q1 + Q2 + Q3；会产生回答模型调用
.\scripts\run-eval.ps1 -TopK 8
```

脚本自行启动 WSL Docker、创建和迁移 `knowbase_eval`，环境变量只在当前 PowerShell
进程内覆盖，退出时恢复。

## 6. 2026-09-20 v2 真实检索结果

运行条件：`BAAI/bge-m3`、1024 维、`top_k=8`、PostgreSQL + pgvector +
pg_trgm。完整原始结果见
`eval/baselines/postgresql-bge-m3-v2.json`。

### 6.1 Q1 检索质量

| 范围 | recall@8 | MRR |
|---|---:|---:|
| overall | **1.000（50/50）** | **0.987** |
| 高等数学 | 1.000 | 0.933 |
| 计算机网络 | 1.000 | 1.000 |
| 操作系统 | 1.000 | 1.000 |
| Python | 1.000 | 1.000 |
| 数据库 | 1.000 | 1.000 |

四档难度的 recall@8 都为 1.000。regular 的 MRR 为 0.967，其余三档为 1.000。
高等数学中有候选排在第 2 或第 3 位，所以整体 MRR 不再是小样本中的理想化 1.000；
50 条库内问题仍全部进入生成层候选。

### 6.2 Q3 阈值扫描

库内问题最高相似度范围约为 **0.543–0.807**，库外问题范围约为
**0.332–0.493**，当前数据上 0.50 位于两组样本之间。报告保留每条样本的完整精度；
文档使用三位小数，避免把远程模型的末位浮动写成稳定承诺。

| τ | 库外拒答率 | 库内误拒率 |
|---:|---:|---:|
| 0.35 | 0.100 | 0.000 |
| 0.40 | 0.200 | 0.000 |
| 0.45 | 0.600 | 0.000 |
| **0.50** | **1.000** | **0.000** |
| 0.55 | 1.000 | 0.020 |
| 0.60 | 1.000 | 0.100 |

因此默认 τ 从 0.45 调整为 **0.50**。它位于当前可分区间内，能让 10 条库外问题都在
L1 截止，同时不误拒 50 条库内问题。0.55 已开始误拒，不能用“阈值越高越安全”的方式
继续上调。

本次归档运行是 retrieval 模式，报告中的 `refusal` 为 `null`。上表是 L1 规则的
精确离线模拟，不代表回答模型的 L2 自检已在 v2 的 60 条样本上重跑。

## 7. 历史结果的适用范围

2026-09-10 的首次完整评估只有 3 篇文档、12 条问题，曾得到 recall/MRR 1.000、库外
拒答率 100%、库内误拒率 0%，并把 τ 从 0.35 调到 0.45。后续审查还修正了来源文档
判断和 MRR 分母。该结果只保留为实现历史，不能再作为当前参数依据。

v2 增加了跨领域的相似库外问题后，证明 τ=0.45 只能拦截 60% 的库外样本。参数必须随
代表性语料重新校准，不能沿用小样本结论。

## 8. 迁移关卡与后续扩展

PostgreSQL → SQLite、pg_trgm → FTS5 或切块算法变更前，先保留本报告；迁移后用同一
清单重跑。最低验收是 recall@8 不低于 1.000、MRR 不显著低于 0.987，并重新报告每库、
每难度结果。若向量模型或相似度实现变化，τ 必须重新扫描，不能把 0.50 当成跨模型常量。

下一轮扩展目标：

- 增至至少 10 个库、100 条问题，增加同义改写、短术语、跨库同名概念与更强对抗样本；
- 在 v2 上运行完整 Q2，归档 L2 拒答、零引用和引用有效性指标；
- 扫描块大小、重叠和召回量，分别记录质量与耗时；
- 为后续 SQLite/FTS5 路线建立与本报告相同 schema 的对照基线。
